1. Introduction

1.1. Purpose

Define the testing approach for the project scope change: the web and mySchneider applications will move from a shared monorepo into two separate repositories.

1.2. Objective

Verify that each application is available from its intended repository and that the separation has not disrupted the application code, required shared components, build and delivery workflows, or interactions between the applications.

1.3. Scope of testing

1.3.1. In Scope testing

  • Confirm that the web application content is present in its designated repository and the mySchneider application content is present in its designated repository.
  • Check repository contents for missing, duplicated, or incorrectly assigned application code and configuration relevant to the separation.
  • Verify that each repository can be checked out and that its configured build, automated checks, and deployment workflow can run independently, where applicable.
  • Validate references to shared code, packages, configuration, and other dependencies after separation.
  • Run agreed application smoke and regression tests after the repository move.
  • Verify any integrations between the web and mySchneider applications that are affected by the repository split.
  • Confirm the agreed repository access and contribution workflows for each application.

1.3.2. Out of scope testing

  • New application features or changes unrelated to the repository separation.
  • Changes to application behavior not required to complete the separation.
  • Infrastructure, platform, or external-system changes not identified as affected by the repository split.

Any additional scope or exclusions must be confirmed by the project team before execution.

1.4. Deliverables

  • Approved test plan and agreed test scope.
  • Test cases and execution evidence for repository separation checks.
  • Build, automated-check, smoke, and regression results for each application, where applicable.
  • Defect records and a test completion summary with open risks or dependencies.

2. Test Strategy

2.1. Testing Levels

  • Repository and configuration verification: check application ownership, repository contents, history or required files, configuration, and dependency references.
  • Build and automated-check verification: run the configured build and automated checks independently for each repository.
  • Application testing: run agreed smoke and regression tests for web and mySchneider after the move.
  • Integration testing: verify affected interactions between the applications and any identified shared components.

The specific frameworks, commands, and test suites are to be confirmed.

2.2. Entry and Exit Criteria

2.2.1. Entry Criteria

  • Both destination repositories are available to the testing team.
  • The intended mapping of monorepo content to the web and mySchneider repositories is agreed.
  • Required branches, access, build instructions, environments, and test data are available or their gaps are recorded.
  • The baseline application versions and the comparison method are identified.

Repository URLs, branch names, baseline identifiers, and approval owners: to be confirmed.

2.2.2. Exit Criteria

  • Planned repository separation checks and agreed application tests have execution results recorded.
  • Build and automated-check results are recorded separately for each repository, where those workflows exist.
  • Defects are documented, triaged, and dispositioned by the project team.
  • Known deviations, unresolved dependencies, and residual risks are communicated to the designated approver.

Required pass rates, defect thresholds, and formal sign-off authority: to be confirmed.

2.3. Suspension and Resumption Criteria

2.3.1. Suspension Criteria

  • A required repository, environment, build workflow, or dependency is unavailable and prevents meaningful execution.
  • Application content or repository mapping is incomplete or materially unclear.
  • A blocking defect prevents the planned test activities from continuing.

2.3.2. Resumption Criteria

  • The blocking access, environment, mapping, or dependency issue has been resolved or an agreed workaround is available.
  • The affected repository or application is ready for the suspended tests to resume.
  • Impact on previously completed results has been assessed and any required retesting is identified.

2.4. System Acceptance Criteria

Acceptance criteria and approval authority must be agreed before test execution. The project should confirm that the application contents are correctly separated, the required workflows operate for both repositories, identified integrations and shared dependencies remain usable, and agreed application tests pass. Any numerical thresholds or mandatory sign-offs are to be confirmed.

2.5. Hardware

No hardware requirements were provided. Test devices or infrastructure requirements, if applicable, are to be confirmed.

2.6. Environment details

Environment names, URLs, configuration, deployment targets, and availability are to be confirmed. Record any environment differences between baseline and post-separation execution.

2.7. Testing tools

Repository hosting, CI/CD, test management, automation, and defect tracking tools were not specified and are to be confirmed.

2.8. Team composition

Test lead, application representatives, repository or build owners, approvers, and other participating roles are to be confirmed.

3. Test Approach

3.1. Baseline Comparison Approach

Use the current monorepo state as the baseline and compare it with the resulting web and mySchneider repositories. Compare the application source and required configuration, then execute equivalent agreed checks against the baseline and separated versions where the same environment and inputs are available.

Baseline commit or release, comparison method, and the handling of intentional changes: to be confirmed.

3.2. Area of Comparison

  • Application source and required repository files are assigned to the correct destination.
  • Required commit history or other migration records are present if preservation is a project requirement.
  • Build scripts, configuration, dependency manifests, and automated checks remain usable in each repository.
  • References to shared components and cross-application integrations resolve correctly.
  • Repository permissions and contribution workflows match the agreed access model.
  • Application behavior remains consistent for the agreed smoke and regression coverage.

3.3. Comparison Conditions

  • Record the source baseline and destination repository revisions used for each run.
  • Use equivalent inputs, test data, environment configuration, and test coverage when comparing baseline and separated versions.
  • Record any differences that are intentional or caused by environment, dependency, or configuration changes.
  • Do not interpret environment or data differences as repository-separation regressions without investigation.

3.4. Test Design

Design tests around the migration mapping and the separation risks. Include checks for correct application ownership, required files and configuration, independent repository checkout and build, dependency resolution, relevant integration points, access, and application smoke/regression behavior. Link each test to the relevant requirement or migration decision once these are available.

3.5. Test Data Strategy

Use the test data already approved for the agreed application smoke and regression tests. Required data, test accounts, and data refresh or masking rules are to be confirmed.

3.5.1. Test Data Management Measures:

  • Identify the data and accounts needed to execute the agreed tests for both applications.
  • Record data dependencies and ensure test data is available in the selected environments before execution.
  • Follow the project's existing data handling and access requirements; details are to be confirmed.

3.6. Test Execution

Capture the repository revision, environment, test identifier, result, evidence, and linked defect for each execution. Execute and report web and mySchneider results independently, then run the agreed cross-application checks.

3.6.1. Baseline Execution

  1. Identify and record the approved monorepo baseline revision.
  2. Run the agreed baseline build, automated checks, and application tests where available.
  3. Record results, environment details, and known baseline failures for comparison.

3.6.2. Dedicated Repository Execution

  1. Check out the web repository and verify its intended content, configuration, and required files.
  2. Run the web repository's configured build and automated checks; record results and defects.
  3. Repeat the equivalent checks independently for the mySchneider repository.
  4. Verify required shared dependencies and affected integrations using the agreed setup.
  5. Compare outcomes with the recorded baseline and investigate differences.

3.6.3. Functional Test case execution Process

  1. Confirm test prerequisites, environment, test data, and application revision.
  2. Execute the agreed smoke or functional test cases for the relevant application.
  3. Record actual results and evidence; log unexpected behavior as a defect.
  4. Retest fixes and document the final result.

3.6.4. Regression Test case execution Process

  1. Select the existing regression coverage agreed for web and mySchneider.
  2. Execute it against the separated repository builds using comparable conditions to the baseline where possible.
  3. Record pass, fail, blocked, and not-run cases, including the reason for any exception.
  4. Assess failures for relation to the repository split and report unresolved impact and risk.

4. Bug Tracking Process

4.1. Bug Tracking tool

Use the project's designated defect tracking tool. Tool and project workspace are to be confirmed.

4.1.1. Priority of Bugs

Assign priority using the project's existing definitions and triage process. Definitions and decision owner are to be confirmed.

4.1.2. Severity of Bugs

Assign severity using the project's existing definitions. Definitions and decision owner are to be confirmed.

4.2. Bug Reporting

For each defect, record a concise title, affected application and repository, repository revision, environment, preconditions, reproduction steps, expected and actual results, supporting evidence, severity and priority per project convention, and related test case. Identify whether the issue is a migration regression, a pre-existing baseline issue, or still under investigation.

5. Assumptions and Dependencies

5.1. Assumptions

  • The stated scope is separation of the existing web and mySchneider applications from one monorepo into two repositories.
  • Application functionality is not intentionally changed as part of this repository separation; confirm this with the project team.
  • Existing application tests and build workflows, if available, can be identified and used or adapted for post-separation verification.
  • Unspecified repository, tooling, environment, ownership, and acceptance details remain open and require confirmation.

5.2. Dependencies

5.2.1. Repository and Source-Code Dependencies

Availability of both destination repositories; agreed mapping of monorepo content; required access; and a decision on whether commit history, tags, or branches must be retained.

5.2.2. Build and CI/CD Dependencies

Build instructions, required secrets or variables, automated checks, and pipeline configuration needed to execute workflows independently in both repositories. Exact tools and pipeline owners are to be confirmed.

5.2.3. Shared and External Component Dependencies

Identification and continued availability of shared code, packages, services, or configuration referenced by either application. The dependency inventory and ownership are to be confirmed.

5.2.4. Environment Dependencies

Access to the required test environments, deployment targets, configuration, and credentials through the project's approved process. Environment details are to be confirmed.

5.2.5. Integration Dependencies

Identification of interactions between web and mySchneider, and any endpoints, contracts, or deployment coordination affected by their residing in separate repositories. Integration owners and test setup are to be confirmed.

5.2.6. Test Data and User Dependencies

Availability of approved test data and the accounts or roles required for the agreed application tests. Data owners and access requirements are to be confirmed.

5.2.7. Team and Process Dependencies

Availability of repository and application owners, testers, build or pipeline support, defect triage participants, and an authorized approver. Named roles, schedule, and sign-off process are to be confirmed.
