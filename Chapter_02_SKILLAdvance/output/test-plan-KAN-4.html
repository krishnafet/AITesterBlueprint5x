1. Scope & Objectives

Purpose: Assess the change that adds SSO and passkey sign-in choices to the existing VWO login page.

Objective: Verify placement and behavior of both options, successful and unsuccessful authentication, passkey availability and device support, safe handling of authentication data, and regressions to existing login options.

Scope of testing: The login-page options and authentication journeys described in KAN-4, including UI visibility, SSO, passkey, error handling, compatibility, security, and the ticket's stated staging Definition of Done.

In scope:

  • Both new buttons appear below "Sign in with Google".
  • Successful and failed SSO authentication, including configured identity providers.
  • Successful passkey authentication, no registered passkey, verification failure, and unsupported browser/device behavior.
  • Responsive presentation, accessibility checks, security protocol use, and exposure of sensitive data in UI or network logs.
  • Regression smoke checks for existing login methods on the same page.

Out of scope: Passkey registration and SSO provider configuration, both explicitly excluded by the story.

Deliverables: This draft test plan and, after review, execution evidence and defect records linked to KAN-4.

4. Test Data & Environment

  • Environment: Staging is specified by the Definition of Done; URL, build, and feature-flag state must be supplied by the team.
  • Data: Dedicated SSO identities for each configured provider; a valid account with a registered passkey; an account without a registered passkey; invalid-credential and failed-verification conditions.
  • Platforms: Product-approved supported and unsupported browser/device combinations, including relevant operating systems and authenticators.
  • Roles / permissions: KAN-4 does not define roles or permission differences. Author confirmation is required before role-specific coverage is added.
  • Handling: Use non-production accounts and synthetic test identities. Never place secrets or real user credentials in screenshots, logs, or defect reports.

5. Risks & Assumptions

Assumptions made: The dashboard is the expected destination for both successful sign-in flows; staging is the execution environment because it is named in DoD; existing Google and email/password methods remain in scope for regression because the new choices are described as additions.

Risks: An undefined support matrix can leave browser/device gaps; unspecified SSO providers limit integration coverage; vague error expectations can produce inconsistent acceptance decisions; authentication defects can create account-access or sensitive-data exposure risks.

6. Entry / Exit Criteria

Entry: KAN-4 implementation is deployed to the agreed staging build; required providers and flags are configured; QA test identities and passkey fixtures are ready; supported platform matrix and error expectations are agreed; test accounts are accessible.

Exit: All agreed scenarios have recorded results; ticket acceptance criteria pass or have linked defects; no open critical/high defects remain per DoD; security checks confirm no sensitive data exposure; deviations and blocked tests are documented; QA owner completes sign-off.

7. Test Strategy

  • Testing levels: UI verification, authentication integration checks, end-to-end system acceptance, browser/device compatibility, accessibility, and focused security validation.
  • System acceptance: Both options are presented in the required order; successful supported flows reach the dashboard; failure and unsupported states provide agreed guidance; security requirements are met.
  • Team composition: QA owner, login/authentication implementation owner, and SSO/identity-provider contact for configuration and test-account support.

8. Test Approach

  • Test design: Requirement-based scenarios mapped to the ticket's UI, SSO, passkey, error, compatibility, and security criteria; supplement with gap-driven exploratory checks after author decisions.
  • Test data strategy: Isolated staging identities and controlled account states; use provider-approved test credentials and registered test authenticators only.
  • Test data management: Keep credentials in approved secret storage; reset or clean up test sessions after execution; redact tokens and personal data from evidence.

9. Bug Tracking Process

  • Tool: Jira, with defects linked to KAN-4 (confirm project workflow and issue type).
  • Priority / severity: Assign using the team's Jira definitions. Treat inability to authenticate or a security exposure as release-blocking candidates pending triage; do not infer the team's exact scale.
  • Reporting: Include build, environment, browser/device, test identity state, steps, expected vs. actual result, and sanitized evidence. Never attach credentials, tokens, or unredacted sensitive logs.

10. Assumptions and Dependencies

  • Assumptions: Successful authentication ends at the dashboard; KAN-4 does not include passkey registration or SSO provider setup; the supplied ticket description and acceptance criteria are the source of truth.
  • Dependencies: Staging deployment; configured SSO providers; identity-provider test accounts; passkey-capable devices and authenticators; agreed browser/device support list; approved security and accessibility criteria.
